# Код и схема

Локальный веб-инструмент для исследования и изменения Java-программ. Загрузите один `.java`-файл, откройте метод на схеме, измените оператор и сравните результат с запуском исходной версии.

Схема строится из дерева разбора JavaParser. Правка схемы проходит проверку javac. Эталон поведения — исходная программа; ИИ и внешняя сеть для анализа и проверки не нужны.

## Запуск на Windows

Нужны **JDK 25** и **Node.js 24 с npm**. Для сервера нужен JDK с компилятором, а не только JRE. Версии библиотек зафиксированы в `pom.xml` и `package-lock.json`.

Из корня проекта в PowerShell:

```powershell
# JAVA_HOME должен указывать на установленную JDK 25.
$env:Path = "$env:JAVA_HOME\bin;$env:Path"

Set-Location frontend
npm ci --no-audit --no-fund
npm run typecheck
npm run check:fixtures
npm run build

Set-Location ..\backend
.\mvnw.cmd -B clean package
java -Duser.language=en -Duser.country=US -Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8 -jar target/blueprints.jar
```

Открыть [localhost:8080](http://localhost:8080). Фронт уже находится внутри JAR. Порт можно изменить переменной окружения `PORT`. Примеры берутся из `../corpus`, `./corpus` либо каталога `CORPUS_DIR`.

Для разработки: сервер запускается отдельно, `npm run dev` в `frontend/` открывает Vite на порту 5173 и проксирует `/api` на 8080.

Dockerfile и compose-файл подготовлены, но запуск Docker в этой проверке не подтверждён.

## Сценарий проверки

1. Открыть пример **MatchDemo.java**, затем метод `countMatches`.
2. Выбрать выражение `Objects.equals(x, y)`: в редакторе выделится точный фрагмент. Кнопка «Править узел» изменяет условие целиком.
3. Заменить условие на `x.equals(y)` и нажать «Запустить и сравнить». Проверка обнаруживает расхождение на входе `null` / `1`.
4. Снова загрузить исходный пример. В находке «Вложенный цикл» выбрать «Индекс частот вместо перебора» и проверить заплатку.
5. Во вкладке «График роста» запустить замер: счётчики циклов оригинала и заплатки на n = 100…1600.
6. На экране «Проверка» нажать «Экспорт теста»: скачается мини-проект Maven с тестами JUnit — по одному на сравнённый вход.

✅ Сквозной прогон собранного JAR (сб 24.10, 20:30):
- правка `x.equals(y)` — 7 расхождений из 41 входа, изменённые операторы выполнены (2 из 2);
- индекс частот — совпало на 41 из 41, выполнены все 7 изменённых операторов;
- замер роста: при n = 1600 тела циклов выполнились 2 561 600 раз до и 3 200 раз после — модели n² и n;
- экспорт: 41 тест; в отдельном пустом Maven-проекте `mvn test` проходит 41 из 41, а если подставить версию с `x.equals(y)`, падают ровно 7.

Это результат конечного набора входов, а не доказательство для любой программы и любых данных.

## Что реализовано

- Карта классов и методов, вложенные блоки управления, дерево выражений с точными диапазонами исходника.
- Оценка сложности O(…) у каждого метода на карте и у каждого цикла на чертеже — по структуре кода: вложенность циклов, вызовы методов из этого же файла, библиотечная сортировка, `contains` у списка, бинарный поиск. В подсказке — откуда оценка; рекурсия помечается, а не угадывается.
- Правка операторов и условий, сохранение выбора узла, ошибки разбора и javac в редакторе.
- Правила R1–R9: вложенный перебор, граница массива, недостижимые private-методы, вероятные ошибки max/min и среднего, присваивание в условии, сравнение строк, целочисленное деление, склейка строки в цикле. У R1 и R9 есть эквивалентные заплатки — их проверка должна дать «совпало»; исправления дефектов идут с намерением BUGFIX. Ограничения и условия показываются в находке.
- Проверка исходной и изменённой версий: stdout, stderr, код выхода, исключение, таймаут, обрезка вывода, повторные прогоны оригинала.
- Покрытие изменённых операторов обеих версий. Неизмеримая правка не получает зелёный результат.
- Замер роста по счётчикам циклов (операции, а не время): модели n, n log n, n² для оригинала и заплатки.
- Экспорт проверки в JUnit: мини-проект Maven с эталоном и тестами «вход → ожидаемый вывод», работает без этого инструмента.
- Программа-меню, которая не завершается на конце ввода, распознаётся по зависанию эталона на 2 разных входах подряд: проверка останавливается и честно сравнивает только сценарии с командой выхода.

Зелёный статус означает «совпало на сравнённых входах». Расхождение показывает кратчайший найденный вход. Жёлтый статус объясняет, чего не хватило для проверки. Исправление дефекта не выдаётся за эквивалентный рефакторинг.

## Проверки и ограничения

✅ Выполнены проверка типов TypeScript, сборка Vite, проверки настоящих и мок-фикстур, полный набор тестов Java (485 тестов, 0 падений, вс 25.10) и сквозной сценарий собранного JAR. Матрица, реальные числа и команды воспроизведения — в [docs/SCOPE.md](docs/SCOPE.md).

Генератор входов использует эвристики по `Scanner`; входы могут не соответствовать незнакомой программе. Заголовки `for`, `switch`, `try`, а также `break`, `continue` и серые блоки пока меняются в коде. Тела лямбд и некоторые бонусные конструкции показаны свёрнуто. Оценка роста в находке — по структуре кода; измеренный рост — по кнопке замера, если в строках находки есть циклы и для формата ввода программы удаётся построить растущие входы; иначе замер честно сообщает, почему не выполнен. Правила находок определяют типы без Symbol Solver: по объявлениям в том же методе и полям, объявленным прямо в классе; в неоднозначных случаях правило молчит, а не угадывает.

Автоматического разбиения монолита на классы нет: улучшения делаются внутри одного файла.

Запускаемый Java-код имеет доступ к файлам и сети компьютера: изолирующей песочницы нет. Программы с явным чтением или печатью стека запускаются настоящей отдельной JVM; их изменённый код пока не получает измерение покрытия.

## Устройство проекта

`backend/` — Java 25, JavaParser, Javalin и Maven Wrapper. `frontend/` — React, TypeScript, Vite и локальный Monaco. `corpus/` — примеры и входы. Регрессионные Java-примеры тестов лежат в `backend/src/test/resources/regressions/` и не зависят от внутренних документов.
